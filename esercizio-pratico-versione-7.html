    24. Esercizio pratico: versione 7

    24.1. Introduzione

    La versione 7 dell’applicazione per il calcolo delle imposte è identica alla versione 6, salvo i seguenti dettagli:

    • il client web invierà contemporaneamente più richieste HTTP. Nella versione precedente queste richieste venivano inviate in sequenza. Il server elaborava quindi in ogni momento una sola richiesta;
    • il server sarà multithread: potrà elaborare più richieste contemporaneamente;
    • per monitorare l’esecuzione di queste richieste, il server web sarà dotato di un logger con cui verranno registrati in un file di testo i momenti salienti dell’elaborazione delle richieste;
    • il server invierà un’e-mail all’amministratore dell’applicazione qualora si verifichi un problema che ne impedisca l’avvio, tipicamente un problema con il database associato al server web;

    24.2. Le utilità

    24.2.1. La classe [Logger]

    La classe [Logger] consentirà di registrare in un file di testo alcune azioni del server web:

    
import codecs
import threading
from datetime import date, datetime
from threading import current_thread

from ImpôtsError import ImpôtsError


class Logger:
    # attributo di classe
    verrou = threading.RLock()

    # costruttore
    def __init__(self, logs_filename: str):
        try:
            # si apre il file in modalità append (a)
            self.__resource = codecs.open(logs_filename, "a", "utf-8")
        except BaseException as erreur:
            raise ImpôtsError(18, f"{erreur}")

    # scrittura di un log
    def write(self, message: str):
        # data/ora corrente
        today = date.today()
        now = datetime.time(datetime.now())
        # nome del thread
        thread_name = current_thread().name
        # non si desidera essere interrotti durante la scrittura nel file di log
        # si richiede l'oggetto di sincronizzazione (= il blocco) della classe: un solo thread lo otterrà
        Logger.verrou.acquire()
        try:
            # scrittura nel log
            self.__resource.write(f"{today} {now}, {thread_name} : {message}")
            # scrittura immediata – altrimenti il testo verrà scritto solo alla chiusura del flusso di scrittura
            # oppure si desidera monitorare i log nel tempo
            self.__resource.flush()
        finally:
            # si libera l'oggetto di sincronizzazione (= il blocco) affinché un altro thread possa ottenerlo
            Logger.verrou.release()

    # rilascio delle risorse
    def close(self):
        # chiusura del file
        if self.__resource:
            self.__resource.close()
    • righe 10-11: si definisce un attributo di classe. Un attributo di classe è una proprietà condivisa da tutte le istanze della classe. Si fa riferimento ad esso con la notazione [Classe.attribut_de_classe] (righe 30, 39). L’attributo di classe [verrou] fungerà da oggetto di sincronizzazione per tutti i thread che eseguono il codice delle righe 31-36;
    • righe 14-19: il costruttore riceve il percorso assoluto del file di log. Il file viene quindi aperto e il descrittore di file recuperato viene memorizzato nella classe;
    • riga 17: il file di log viene aperto in modalità «append» (a). Ogni riga scritta verrà aggiunta alla fine del file;
    • righe 22-39: il metodo [write] consente di scrivere nel file di log un messaggio passato come parametro. A questo vengono aggiunte due informazioni:
      • riga 24: la data odierna;
      • riga 25: l’ora corrente;
      • riga 27: il nome del thread che scrive il log. Non bisogna dimenticare che un’applicazione web serve più utenti contemporaneamente. A ogni richiesta viene assegnato un thread per l’esecuzione. Se questo thread viene messo in pausa, tipicamente per un’operazione di I/O (rete, file, database), allora il processore verrà assegnato a un altro thread. A causa di queste possibili interruzioni, non si può essere certi che un thread riesca a scrivere una riga nel file di log senza essere interrotto. Si rischia quindi di vedere i log di due thread diversi mescolarsi. Il rischio è basso, forse addirittura nullo, ma abbiamo comunque deciso di mostrare come sincronizzare l’accesso di due thread a una risorsa comune, in questo caso il file di log;
    • riga 30: prima di scrivere, il thread richiede la chiave della porta d’ingresso. La chiave richiesta è quella creata alla riga 11. È effettivamente unica: un attributo di classe è unico per tutte le istanze della classe;
      • al tempo T1, un thread Thread1 ottiene la chiave. Può quindi eseguire la riga 33;
      • al tempo T2, il thread Thread1 viene messo in pausa prima ancora di aver terminato la scrittura del log;
      • al tempo T3, anche il thread Thread2, che ha ottenuto il processore, deve scrivere un log. Giunge così alla riga 30, dove richiede la chiave della porta d’ingresso. Gli viene risposto che un altro thread la possiede già. Viene quindi automaticamente messo in pausa. Lo stesso accadrà a tutti i thread che richiederanno questa chiave;
      • al tempo T4, il thread Thread1, che era stato messo in pausa, riacquista il processore. A questo punto completa la scrittura del log;
    • righe 32-36: la scrittura nel file di log avviene in due fasi:
    • riga 33: il descrittore di file ottenuto alla riga 17 opera con un buffer. L’operazione [write] della riga 33 scrive in questo buffer ma non direttamente nel file. Il buffer viene poi svuotato nel file a determinate condizioni:
          • il buffer è pieno;
          • il descrittore di file è oggetto di un'operazione [close] o [flush];
    • riga 36: si forza la scrittura della riga di log nel file. Si procede in questo modo perché si desidera vedere i log dei diversi thread intercalarsi tra loro. Se non si facesse così, i log di un thread verrebbero scritti tutti contemporaneamente alla chiusura del descrittore, riga 45. Sarebbe quindi molto più difficile rendersi conto che alcuni thread sono stati arrestati: bisognerebbe controllare gli orari nei log;
    • riga 39: il thread Thread1 restituisce la chiave che gli era stata assegnata. Questa potrà essere assegnata a un altro thread;
    • riga 22: il metodo [write] è quindi sincronizzato: un solo thread alla volta scrive nel file di log. La chiave del meccanismo è la riga 30: qualunque cosa accada, solo un thread recupera la chiave per passare alla riga successiva. La conserva finché non la restituisce (riga 39);
    • righe 41-45: il metodo [close] consente di liberare le risorse allocate al descrittore del file di log;

    La classe [SendAdminMail] riceve il dizionario dalle righe 2-13 e la configurazione per l’invio dell’e-mail. La classe è la seguente:

    
# importazioni
import smtplib
from email.mime.text import MIMEText
from email.utils import formatdate


class SendAdminMail:

    # -----------------------------------------------------------------------
    @staticmethod
    def send(config: dict, message: str, verbose: bool = False):
        # invia un messaggio al server SMTP config['smtp-server'] sulla porta config[smtp-port]
        # se config['tls'] è vero, verrà utilizzato il supporto TLS
        # l’e-mail viene inviata a nome di config['from']
        # al destinatario config['to']
        # il messaggio ha come oggetto config['subject']
        # si trova il riferimento a un logger in config['logger']

        # si recupera il logger dalla configurazione - può essere uguale a None
        logger = config["logger"]
        # server SMTP
        server = None
        # si invia il messaggio
        try:
            # il server SMTP
            server = smtplib.SMTP(config["smtp-server"])
            # modalità verbosa
            server.set_debuglevel(verbose)
            # connessione sicura?
            if config['tls']:
                # inizio della procedura di sicurezza
                server.starttls()
                # autenticazione
                server.login(config["user"], config["password"])
            # creazione di un messaggio Multipart - è questo il messaggio che verrà inviato
            msg = MIMEText(message)
            msg['From'] = config["from"]
            msg['To'] = config["to"]
            msg['Date'] = formatdate(localtime=True)
            msg['Subject'] = config["subject"]
            # invio del messaggio
            server.send_message(msg)
            # log - il logger potrebbe non esistere
            if logger:
                logger.write(f"[SendAdminMail] Message envoyé à [{config['to']}] : [{message}]\n")
        except BaseException as erreur:
            # log - il logger potrebbe non esistere
            if logger:
                logger.write(
                    f"[SendAdminMail] Erreur [{erreur}] lors de l'envoi à [{config['to']}] du message [{message}] : \n")
        finally:
            # operazione completata - si liberano le risorse utilizzate dalla funzione
            if server:
                server.quit()

    La funzione [index] (riga 114) è la seguente:

    
# Home URL
@app.route('/', methods=['GET'])
@auth.login_required
def index():
    logger = None
    try:
        # registrazione
        logger = Logger(config["logsFilename"])
        # lo si memorizza in una configurazione associata al thread
        thread_config = {"logger": logger}
        thread_name = threading.current_thread().name
        config[thread_name] = {"config": thread_config}
        # si registra la richiesta
        logger.write(f"[index] requête : {request}\n")
        # si interrompe il thread se richiesto
        sleep_time = config["sleep_time"]
        if sleep_time != 0:
            # la pausa è casuale, in modo che alcuni thread vengano interrotti e altri no
            aléa = randint(0, 1)
            if aléa == 1:
                # registrazione prima della pausa
                logger.write(f"[index] mis en pause du thread pendant {sleep_time} seconde(s)\n")
                # pausa
                time.sleep(sleep_time)
        # la richiesta viene eseguita da un controller
        résultat, status_code = index_controller.execute(request, config)
        # Si è verificato un errore irreversibile?
        if status_code == status.HTTP_500_INTERNAL_SERVER_ERROR:
            # si invia un'e-mail all'amministratore dell'applicazione
            config_mail = config["adminMail"]
            config_mail["logger"] = logger
            SendAdminMail.send(config_mail, json.dumps(résultat, ensure_ascii=False))
        # si registra la risposta
        logger.write(f"[index] {résultat}\n")
        # si invia la risposta
        return json_response(résultat, status_code)
    except BaseException as erreur:
        # si registra l'errore, se possibile
        if logger:
            logger.write(f"[index] {erreur}")
        # si prepara la risposta al cliente
        résultat = {"réponse": {"erreurs": [f"{erreur}"]}}
        # si invia la risposta
        return json_response(résultat, status.HTTP_500_INTERNAL_SERVER_ERROR)
    finally:
        # si chiude il file di log se è stato aperto
        if logger:
            logger.close()

Questo thread può essere interrotto e messo in pausa in qualsiasi momento per riprendere l’esecuzione poco dopo. È importante tenere sempre presente questo aspetto quando il codice accede a una risorsa condivisa da tutti i thread. In questo caso, tale risorsa è il file di log: tutti i thread vi scrivono;
    • riga 8: si crea un’istanza del logger. Pertanto, ogni thread avrà un’istanza diversa del logger. Tuttavia, tutti questi logger puntano allo stesso file di log. È comunque importante notare che quando un thread chiude il proprio logger, ciò non ha alcuna ripercussione sui logger degli altri thread;
    • righe 9-12: si memorizza il logger nel dizionario [config] dell’applicazione, associato a una chiave che riporta il nome del thread. Pertanto, se vi sono n thread in esecuzione simultanea, verranno create n voci nel dizionario [config]. [config] è una risorsa condivisa tra tutti i thread. Potrebbe quindi essere necessaria una sincronizzazione. Qui ho formulato un'ipotesi. Ho supposto che se due thread creassero contemporaneamente la propria voce nel file [config] e uno dei due venisse interrotto dall’altro, ciò non avrebbe alcuna conseguenza. Il thread interrotto avrebbe potuto completare in un secondo momento la creazione della voce. Se l’esperimento dimostrasse che questa ipotesi è errata, sarebbe necessario sincronizzare l’accesso alla riga 12;

      • si prende quindi il minimo dei due valori;

      • [slice(10,12)] è l’insieme degli indici [10, 11, 12];
      • [taxpayers[slice(10,12)]] è l'elenco [taxpayers[10], taxpayers[11], taxpayers[12];

    • riga 51: il thread viene avviato. Verrà quindi eseguito in parallelo agli altri thread attivi. In questo caso, eseguirà la funzione [thread_function] con gli argomenti che gli sono stati forniti;
    • righe 53-54: il thread principale attende il completamento di ciascuno dei thread che ha avviato. Facciamo un esempio:
      • il thread principale ha avviato tre thread [th1, th2, th3];
      • il thread principale rimane in attesa di ciascuno dei thread (righe 53-54) nell’ordine del ciclo for: [th1, th2, th3];
      • supponiamo che i thread terminino nell’ordine [th2, th1, th3];
      • il thread principale attende il completamento di th1. Quando th2 termina, non accade nulla;
      • quando th1 termina, il thread principale entra in attesa di th2. Tuttavia, quest’ultimo è già terminato. Il thread principale passa quindi al thread successivo e attende th3;
      • quando th3 termina, il thread principale ha terminato l’attesa e passa quindi all’esecuzione della riga 57;

      • riga 43: la lista [thread_payers] associata a un thread contiene copie dei riferimenti agli oggetti presenti nella lista [taxpayers];

# esecuzione del livello [dao] in un thread
# taxpayers è un elenco di contribuenti
def thread_function(dao, logger, taxpayers: list):
    # log di inizio del thread
    thread_name = threading.current_thread().name
    logger.write(f"début du thread [{thread_name}] avec {len(taxpayers)} contribuable(s)\n")
    # si calcola l'imposta dei contribuenti
    for taxpayer in taxpayers:
        # log
        logger.write(f"début du calcul de l'impôt de {taxpayer}\n")
        # calcolo sincrono dell'imposta
        dao.calculate_tax(taxpayer)
        # log
        logger.write(f"fin du calcul de l'impôt de {taxpayer}\n")
    # log fine del thread
    logger.write(f"fin du thread [{thread_name}]\n")

      • [logger]: un riferimento al logger. Questo dato è condiviso;
      • [taxpayers]: un elenco di contribuenti. Questo dato non è condiviso: ogni thread gestisce un elenco diverso;

      • il riferimento [logger] punta a un descrittore di file. Abbiamo visto che poteva verificarsi un problema durante la scrittura dei log nel file. Per questo motivo la scrittura nel file è stata sincronizzata;

    • righe 8-14: calcolo dell’imposta dei contribuenti;

    • questi log mostrano che sono stati avviati cinque thread per calcolare l’imposta di 11 contribuenti. Questi cinque thread hanno inviato richieste simultanee al server di calcolo dell’imposta. È necessario comprendere come funziona:
      • il thread [Thread-1] viene avviato per primo. Quando ha il controllo del processore, procede nell’esecuzione del codice fino a inviare la sua richiesta HTTP. Poiché deve attendere il risultato di tale richiesta, viene automaticamente messo in attesa. A quel punto perde il controllo del processore, che viene acquisito da un altro thread;
      • righe 1-10: lo stesso processo si ripete per ciascuno dei 5 thread. In questo modo i 5 thread vengono avviati prima ancora che il thread [Thread-1] abbia ricevuto la sua risposta (riga 11);
    • i thread non terminano nell'ordine in cui sono stati avviati. Pertanto, è il thread [Thread-3] a terminare per primo, alla riga 23;
