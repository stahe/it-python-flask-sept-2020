    29. Esercizio pratico: versione 11

    29.1. Introduzione

    Nelle versioni precedenti dell’applicazione client/server per il calcolo delle imposte, il livello [métier] che implementa le regole di business di tale calcolo era sul lato server. Ora si propone di spostarlo sul lato client. Qual è il vantaggio? Parte del lavoro svolto dal server verrà trasferito sul lato client. Se si considera la situazione di un server interpellato da N client, N calcoli fiscali saranno effettuati dai client. Nelle versioni precedenti, il server eseguiva questi N calcoli fiscali. Poiché non esegue più il calcolo fiscale, il server risponderà più rapidamente ai propri client e potrà quindi servirne un numero maggiore contemporaneamente.

    L’architettura client/server diventa la seguente:

    • il livello [métier] [10] è stato duplicato come [12] sul client;
    • è stato aggiunto al client un nuovo script [main2] [11];

    Il client web avrà due modi per calcolare l’imposta dall’elenco dei contribuenti presente in [3]:

    • utilizzare il metodo della versione precedente. Questo metodo si avvale del livello [métier] [10] del server. Lo script [main] utilizzerà questo metodo;
    • limitarsi a richiedere al server i dati dell’amministrazione fiscale [2-4] e poi utilizzare il livello [métier] [12] locale sul client;

    Confronteremo le prestazioni dei due metodi.

    29.2. Il server web

    La struttura ad albero del server web sarà la seguente:

    • La cartella [http-servers/06] viene inizialmente creata tramite copia della cartella [http-servers/05]. Si manterrà infatti quanto acquisito dalla precedente versione 10. Si aggiungerà semplicemente una nuova funzionalità. Questa si concretizza nella presenza di un nuovo controller [get_admindata_controller] [1]. L’altro controller [calculate_tax_controller] non è altro che il vecchio controller [index_controller], che è stato rinominato;

    29.3. Configurazione

    Il server metterà a disposizione due URL di servizio:

    • [/calculate-tax] per calcolare l’imposta su un elenco di contribuenti passato nel corpo di un POST. Corrisponde quindi al URL [/] della precedente versione 10;
    • [/get-admindata] genera la stringa jSON contenente i dati dell’amministrazione fiscale;

    La configurazione [config] associa ciascuno di questi URL al controller che lo elabora:

    
    # dizionario dei controller dell'applicazione web
    import calculate_tax_controller, get_admindata_controller
    controllers = {"calculate-tax": calculate_tax_controller, "get-admindata": get_admindata_controller}
    config['controllers'] = controllers

        logger.write("fin du calcul de l'impôt des contribuables\n")
        # chiusura del logger
        logger.close()
    # Operazione completata
    print("Travail terminé...")
    • righe 26-27: si recuperano i dati dell’amministrazione fiscale dal server;
    • righe 28-31: successivamente il calcolo dell’imposta dei contribuenti viene effettuato localmente;

    29.9. Test del client

    In ciascuno degli script [main, main2] si registrano l’inizio e la fine dello script. In questo modo sarà possibile calcolare la durata di esecuzione dello script. Facciamo alcune previsioni:

    • lo script [main] della versione precedente:
      • crea N thread che vengono eseguiti simultaneamente;
      • ogni thread elabora un lotto di contribuenti per i quali fa calcolare l’imposta tramite un’unica richiesta al server;
      • poiché i N thread vengono eseguiti simultaneamente, la richiesta N+1 viene lanciata prima che la richiesta N abbia ricevuto la risposta. Pertanto, le N richieste comportano un costo maggiore rispetto a una singola richiesta, ma probabilmente non di molto. Inoltre, sul server vengono eseguiti 11 (il numero dei contribuenti) calcoli di business;
    • lo script [main2] di questa versione:
      • effettua un'unica richiesta al server;
      • esegue 11 calcoli di business localmente sul client;

    I calcoli di business avranno la stessa durata sia sul server che sul client. La differenza si avrà quindi a livello delle richieste. Ci si può quindi aspettare che il tempo di esecuzione di [main] sia leggermente superiore a quello di [main2].

    Si avvia il server della versione 11, il SGBD e il server di posta [hMailServer]. Sul lato server, si imposta il parametro [sleep_time] a zero affinché entrambi i test vengano eseguiti nelle stesse condizioni.
