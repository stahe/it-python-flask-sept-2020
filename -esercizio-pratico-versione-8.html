    25. Esercizio pratico: versione 8

    25.1. Introduzione

    Scriveremo una nuova applicazione client/server. La novità del server è che gestirà una sessione. Invece di inserire i dati dell’amministrazione fiscale in un oggetto con ambito [application], li inseriremo in un oggetto con ambito [session]. In questo modo, si registra un calo delle prestazioni del codice. Quando un oggetto può essere condiviso in sola lettura da tutti gli utenti, è preferibile definirlo come oggetto con ambito [application] piuttosto che con ambito [session]. Si ottiene almeno un risparmio in termini di larghezza di banda, poiché in questo modo si riduce la dimensione del cookie di sessione. Tuttavia, vogliamo illustrare un’applicazione client/server in cui il client e il server si scambiano un cookie di sessione.

    25.3.1.1. La classe [ImpôtsDaoWithHttpSession]

    Il livello [dao] è implementato dalla seguente classe [ImpôtsDaoWithHttpSession]:

    
# importazioni

import requests
from flask_api import status
from myutils import decode_flask_session

from AbstractImpôtsDao import AbstractImpôtsDao
from AdminData import AdminData
from ImpôtsError import ImpôtsError
from InterfaceImpôtsMétier import InterfaceImpôtsMétier
from TaxPayer import TaxPayer


class ImpôtsDaoWithHttpSession(AbstractImpôtsDao, InterfaceImpôtsMétier):

    # costruttore
    def __init__(self, config: dict):
        # inizializzazione del genitore
        AbstractImpôtsDao.__init__(self, config)
        # memorizzazione degli elementi di configurazione
        # configurazione generale
        self.__config = config
        # server
        self.__config_server = config["server"]
        # modalità debug
        self.__debug = config["debug"]
        # registratore
        self.__logger = None
        # cookie
        self.__cookies = None

    # metodo inutilizzato
    def get_admindata(self) -> AdminData:
        pass

    # calcolo dell'imposta
    def calculate_tax(self, taxpayer: TaxPayer, admindata: AdminData = None):
        # si consentono le eccezioni
        # parametri del GET
        params = {"marié": taxpayer.marié, "enfants": taxpayer.enfants, "salaire": taxpayer.salaire}
        # connessione con autenticazione Auth Basic?
        if self.__config_server['authBasic']:
            response = requests.get(
                # URL del server interrogato
                self.__config_server['urlServer'],
                # parametri di URL
                params=params,
                # autenticazione Basic
                auth=(
                    self.__config_server["user"]["login"],
                    self.__config_server["user"]["password"]),
                cookies=self.__cookies)

        else:
            # connessione senza autenticazione Auth Basic
            response = requests.get(self.__config_server['urlServer'], params=params, cookies=self.__cookies)
        # si recuperano i cookie dalla risposta, se presenti
        if response.cookies:
            self.__cookies = response.cookies
            # si recupera il cookie di sessione
            session_cookie = response.cookies.get('session')
            # lo si decodifica per effettuare l'accesso
            if session_cookie:
                # funzione di accesso
                if not self.__logger:
                    self.__logger = self.__config['logger']
                # si effettua il login
                self.__logger.write(f"cookie de session={decode_flask_session(session_cookie)}\n")

        # modalità debug?
        if self.__debug:
            # registratore
            if not self.__logger:
                self.__logger = self.__config['logger']
            # si registra
            self.__logger.write(f"{response.text}\n")
        # codice di stato della risposta HTTP
        status_code = response.status_code
        # si inserisce la risposta jSON in un dizionario
        résultat = response.json()
        # errore se il codice di stato è diverso da 200 OK
        if status_code != status.HTTP_200_OK:
            # si sa che gli errori sono stati associati alla chiave [erreurs] della risposta
            raise ImpôtsError(87, résultat['réponse']['erreurs'])
        # si sa che il risultato è stato associato alla chiave [result] della risposta
        # si modifica il parametro di input con questo risultato
        taxpayer.fromdict(résultat["réponse"]["result"])
    • riga 30: il livello [dao] gestirà un dizionario di cookie;
    • riga 58: la proprietà [response.cookies] è un dizionario che raccoglie i cookie inviati dal server nelle intestazioni HTTP e [Set-Cookie];
    • riga 59: questi cookie vengono memorizzati nel livello [dao]. Verranno rinviati al server in occasione delle successive richieste dello stesso client;
    • righe 60-68: sebbene non sia indispensabile, si recupera il cookie di sessione. Nel dizionario dei cookie inviati dal server, il cookie di sessione è associato alla chiave [session];
    • righe 62-68: si decodifica il cookie di sessione per effettuare il login;
    • riga 68: torneremo in seguito sulla funzione [decode_flask_session] che decodifica il cookie di sessione;
    • righe 52 e 57: ad ogni richiesta dello stesso client, i cookie inviati dal server gli vengono rinviati. È in questo modo che la sessione Flask viene mantenuta tra il client e il server;

    Ora bisogna tenere presente che il livello [dao] verrà eseguito simultaneamente da più thread. È quindi necessario esaminare tutte le proprietà dell’istanza di classe e verificare se l’accesso simultaneo a tali proprietà pone dei problemi. Qui abbiamo aggiunto la proprietà [self.__cookies], alla riga 30. Questa proprietà viene modificata alla riga 59. Abbiamo quindi un accesso in scrittura a un dato condiviso da tutti i thread. Tuttavia, questo accesso pone un problema: ogni thread che rappresenta un determinato client ha il proprio cookie di sessione. Infatti, al suo interno è presente un numero di cliente (=thread) univoco per ogni cliente. Se non si interviene, il thread T2 può sovrascrivere i cookie del thread T1.

    Abbiamo già visto un metodo per gestire questo problema: è possibile creare nel file [config], passato come parametro al costruttore (riga 17), chiavi diverse per ogni thread. Ad esempio, si può utilizzare come chiave il nome del thread:

    • alla riga 59, si potrebbe scrivere: 
    
config[thread_name][‘cookies’]=cookies
    • alla riga 52 si potrebbe quindi scrivere: 
    
cookies=config[thread_name][‘cookies’]

    Qui useremo una tecnica diversa: ogni thread (=cliente) avrà il proprio livello [dao]. In questo modo la riga 59 non pone più alcun problema, poiché i cookie utilizzati sono quelli di un unico cliente.

    A tal fine, creeremo una nuova classe [ImpôtsDaoWithHttpSessionFactory].

    25.3.1.2. La funzione di decodifica della sessione Flask

    La funzione [decode_flask_session] è definita nello script [myutils]:

    Abbiamo già esaminato lo script |myutils|. Questo script è un modulo a livello di macchina che i vari script di questo corso possono importare con l’istruzione:

    In esso si definisce la funzione [decode_flask_session] nel modo seguente:

    
def decode_flask_session(cookie: str) -> str:
    # fonte: https://www.kirsle.net/wizards/flask-session.cgi
    compressed = False
    payload = cookie

    if payload.startswith('.'):
        compressed = True
        payload = payload[1:]

    data = payload.split(".")[0]

    data = base64_decode(data)
    if compressed:
        data = zlib.decompress(data)

    return data.decode("utf-8")
